# Docker Monitoring and Resource Management Study Guide

This guide covers essential tools and commands for monitoring running containers, analyzing resource consumption, and enforcing limits to ensure host stability.

-----

## Lecture 1: Analyzing Application Output with Docker Logs

When running containers in **detached mode** (`-d`), you lose the real-time console output. The `logs` command allows you to retrieve this information for debugging and auditing.

### Core Concepts

  * **Standard Output (stdout)**: Most Dockerized applications are configured to write their logs to stdout, which Docker captures and stores.
  * **Detached Monitoring**: The ability to check on background processes without having them occupy your current terminal session.

### Syntax & Examples

**Basic Log Retrieval:**

``` bash
# View all logs generated by a container since it started
docker logs [CONTAINER_ID_OR_NAME]

```

**Real-time Following:**

``` bash
# Stream logs in real-time (similar to 'tail -f')
docker logs -f [CONTAINER_ID_OR_NAME]

```

**Partial Retrieval:**

``` bash
# View only the last 5 entries
docker logs --tail 5 [CONTAINER_ID_OR_NAME]

```

### Deep Explanation

Think of `docker logs` as a "DVR" for your container's terminal. Even if you weren't watching when the application printed an error message, Docker recorded it. Using the `-f` (follow) flag turns the DVR into a "Live Feed."

### Key Takeaways

  * Use `docker logs` to diagnose why a background container might be failing.
  * **Ctrl + C** is used to exit the "follow" mode.

### Summary Notes

`docker logs` provides visibility into the internal activity of detached containers, allowing for both historical review and live monitoring of application output.

## Lecture 2: Real-time Resource Monitoring with Docker Stats

It is common for containers to consume more resources than expected. `docker stats` provides a live dashboard of how much "fuel" each container is taking from your host machine.

### Core Concepts

  * **Resource Utilization**: The actual amount of CPU and RAM being used by a container at a given moment.
  * **Host Stability**: Monitoring stats helps prevent "noisy neighbor" scenarios where one container slows down the entire computer.

### Syntax & Examples

**Viewing the Dashboard:**

``` bash
# View a live data stream for all running containers
docker stats

```

**Testing with Stress-ng:**

``` bash
# Create a high CPU load (2 CPU workers for 10 minutes)
docker run -d --name cpu-stress alexeiled/stress-ng --cpu 2 --timeout 10m

# Create a high Memory load (1GB of RAM)
docker run -d --name mem-stress alexeiled/stress-ng --vm 1 --vm-bytes 1G --timeout 10m

```

### Deep Explanation

The `docker stats` output displays a table with the following critical columns:

  * **CPU %**: Percentage of the host's CPU power used.
  * **MEM USAGE / LIMIT**: The current RAM used vs. the total allowed.
  * **NET I/O**: Network traffic sent and received.
  * **BLOCK I/O**: Data written to or read from the hard drive.

### Key Takeaways

  * `docker stats` is the first tool you should use if your computer feels slow after starting Docker containers.
  * It provides a **container-level** overview of health.

### Summary Notes

`docker stats` is essential for production environments to ensure containers are operating within expected resource boundaries.

## Lecture 3: Process Inspection with Docker Top

While `stats` shows the health of the container "box," `top` shows you exactly what programs are running *inside* that box.

### Core Concepts

  * **Process Identification**: Distinguishing between the main application and any helper scripts or side-processes.
  * **Granular Inspection**: Seeing which specific internal process is responsible for the CPU spikes noted in `docker stats`.

### Syntax & Examples

**Inspecting Internal Processes:**

``` bash
# Show processes running inside the container
docker top [CONTAINER_NAME]

```

### Deep Explanation: Stats vs. Top

| Feature      | `docker stats`                          | `docker top`                                              |
| :----------- | :-------------------------------------- | :-------------------------------------------------------- |
| **Focus**    | The container as a whole.               | Individual processes inside.                              |
| **Metric**   | CPU/RAM/IO percentages.                 | PID, User, and Command details.                           |
| **Best For** | Finding which container is the problem. | Finding which script inside the container is the problem. |

### Key Takeaways

  * Use `top` when you need to see the process ID (PID) or the specific command string that started a process.
  * It helps confirm if your application spawned multiple workers or if a script is hanging.

### Summary Notes

`docker top` bridges the gap between high-level container monitoring and low-level system process management.

## Lecture 4: Enforcing Resource Limits

If an application is poorly optimized or "leaky," you can use Docker to "sandbox" it, ensuring it cannot crash your host machine by taking too much memory or CPU.

### Core Concepts

  * **Hard Limits**: Strict boundaries that a container cannot cross.
  * **Resource Throttling**: Restricting a container to a fraction of a CPU core.

### Syntax & Examples

**Limiting CPU and Memory:**

``` bash
# Limit the container to only 1/4th of a CPU core
docker run -d --cpus="0.25" --name cpu-limited alexeiled/stress-ng --cpu 2

```

**Common Flags:**

  * `--memory`: Limits the RAM (e.g., `--memory="512m"`).
  * `--cpus`: Limits the CPU time (e.g., `--cpus="0.5"`).

### Common Mistakes

  * **Confusing Flags**: Ensure you place Docker flags (like `--cpus`) *before* the image name. Arguments placed *after* the image name (like `--cpu 2`) are passed to the application inside, not to Docker itself.
  * **Setting Limits Too Low**: If you set memory limits too low, the Linux kernel may kill the container (OOM Kill).

### Key Takeaways

  * Resource limits are crucial for production settings to maintain environment health.
  * Use `docker stats` after applying limits to verify they are working (e.g., seeing CPU usage capped at 25%).

### Summary Notes

Enforcing resource limits provides a safety net, allowing you to run potentially unstable code without risking the entire infrastructure.

## Final Overall Docker Debugging Cheat Sheet

| Command                     | Purpose                    | When to use                                     |
| :-------------------------- | :------------------------- | :---------------------------------------------- |
| `docker logs -f [ID]`       | Stream application output. | When the app isn't behaving as expected.        |
| `docker logs --tail N [ID]` | View last N log lines.     | To quickly see the most recent errors.          |
| `docker stats`              | Live resource dashboard.   | When the host machine is slow/unresponsive.     |
| `docker top [ID]`           | List internal processes.   | To see which specific script is running inside. |
| `docker run --cpus="X"`     | Limit CPU usage.           | To prevent a container from hogging the CPU.    |
| `docker run --memory="X"`   | Limit RAM usage.           | To prevent a container from hogging memory.     |

**Pro Tip:** Always run `docker ps` first to get the correct container name or ID before using any of the commands above.
